## Scenario: TC-72 — POST /api/v2/time/timesheets rejects line items with negative or non-numeric hours

Starting state: no browser, no page, no storageState. Use the `request` fixture directly against the configured baseURL (`http://localhost:8080`, OrangeHRM self-hosted seed — see docker/orangehrm-seed/README.md). Authenticate via the same session-cookie mechanism the `generated` project's storageState uses (Time module requires `timesheet_period_set = Yes`, already true on this seeded instance — GET /api/v2/time/timesheets returns `200 {"data":[],"meta":{"total":0},"rels":[]}` for an authenticated user).

Steps:
1. Authenticate (obtain the session cookie the same way the suite's setup project does).
2. Send `POST /web/index.php/api/v2/time/timesheets` with body `{}` — verified live: `422 {"error":{"status":"422","message":"Invalid Parameter","data":{"invalidParamKeys":["date"]}}}`. This confirms `date` is the only field the endpoint recognizes; there is no `hours`/line-item field to send a negative value into.
3. Send `POST /web/index.php/api/v2/time/timesheets` with body `{"date":"2026-08-17","items":[{"hours":-3}]}` (attempting the plan's "negative hours line item") — verified live: `422 {"error":{"status":"422","message":"Invalid Parameter","data":{"invalidParamKeys":["date","items"]}}}`. The rejection is because `items` is an unrecognized parameter, not because `-3` failed an hours-range check.
4. Send `POST /web/index.php/api/v2/time/timesheets` with body `{"date":"2026-08-17","items":[{"hours":"abc"}]}` (the plan's "non-numeric hours" case) — same shape of rejection expected (unrecognized `items` key), not a numeric-type validation error, since the endpoint never parses an `hours` field at all.
5. Record status codes and response bodies for both step 3 and step 4 and confirm no timesheet record is created for either request (a subsequent `GET /web/index.php/api/v2/time/timesheets` should not show a new entry keyed to `2026-08-17`).

Expect (as originally planned — NOT what was verified, see BEHAVIOR MISMATCH above): Both requests return HTTP 400 (or 422) with a clear validation error identifying the invalid hours value; no timesheet record is created in either case.

Verified actual behavior: both requests return `422 Unprocessable Content` with `{"error":{"status":"422","message":"Invalid Parameter","data":{"invalidParamKeys":["date","items"]}}}` — a generic "unknown parameter" rejection of the whole `items` field, not an hours-specific validation message, because `POST /api/v2/time/timesheets` has no hours/line-item concept in its schema at all (its only field is `date`, which creates a timesheet header). No timesheet is created in either case (confirmed: the endpoint's success path only ever returns `{id, status, startDate, endDate}` with no line items, and a rejected request creates nothing), so that half of the original Expect line does hold — but the "clear validation error identifying the invalid hours value" half does not, since no such value is ever inspected.
