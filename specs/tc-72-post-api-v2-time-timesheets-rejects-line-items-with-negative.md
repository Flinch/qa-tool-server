## Scenario: TC-72 — POST /api/v2/time/timesheets rejects line items with negative or non-numeric hours

Starting state: no browser, no page, no storageState. Configured baseURL: `http://localhost:8080/` (this project's `api_base_url`). No API-auth helper exists yet for this project (`helpers/project-7/` only has page-based `loginAs.ts`, `createEmployee.ts`, `createCandidate.ts`, `createVacancy.ts`) — auth for this test is the raw HTTP flow verified live below, not a browser login.

Steps:
1. Authenticate via the app's real session-cookie flow (there is no bearer-token auth on this API): `GET /web/index.php/auth/login`, extract the CSRF `_token` from the `<auth-login :token="...">` component in the returned HTML, then `POST /web/index.php/auth/validate` (form-urlencoded body: `_token`, `username=qatooladmin`, `password=QaTool2026!Seed` — or `TEST_USER_NAME`/`TEST_USER_PASSWORD`/fallback per this project's credentials). Verified live: returns `302` redirecting to `/web/index.php/dashboard/index` and sets an `_orangehrm` session cookie (`HttpOnly`, path `/web`) — send this cookie on every subsequent request in this test.
2. Create the prerequisite time-tracking data this test needs (unique values, since the test creates what it uses): `POST /api/v2/time/customers` with `{"name": "<unique customer name>", "description": "..."}` → verified live: `200` with `{"data":{"id":<customerId>,"name":...,"description":...,"deleted":false}}`. Then `POST /api/v2/time/projects` with `{"name": "<unique project name>", "description": "...", "customerId": <customerId>, "projectAdminsEmpNumbers": []}` → verified live: `200` with `{"data":{"id":<projectId>,"name":...,"customer":{...},"deleted":false,"projectAdmins":[]}}`. Then `POST /api/v2/time/project/<projectId>/activities` (note: singular `/project/`, unlike every other `/api/v2/time/projects...` route — verified live, a `POST /api/v2/time/projects/<projectId>/activities` on the plural path 404s) with `{"name": "<unique activity name>"}` → verified live: `200` with `{"data":{"id":<activityId>,"name":...,"deleted":false}}`.
3. Create the timesheet container: `POST /api/v2/time/timesheets` with `{"date": "<any date in the target week>"}`. Verified live: `200` with `{"data":{"id":<timesheetId>,"status":{"id":"NOT SUBMITTED","name":"Not Submitted"},"startDate":"<weekStart>","endDate":"<weekEnd>"}}`.
4. Attempt to record a negative-hours line item: `PUT /api/v2/time/timesheets/<timesheetId>/entries` with body `{"entries":[{"projectId":<projectId>,"activityId":<activityId>,"dates":{"<date-in-period>":{"duration":"-3:00"}}}],"deletedEntries":[]}`.
5. Record the HTTP status code and response body from step 4.
6. Attempt to record a non-numeric-hours line item: `PUT /api/v2/time/timesheets/<timesheetId>/entries` with body `{"entries":[{"projectId":<projectId>,"activityId":<activityId>,"dates":{"<date-in-period>":{"duration":"abc"}}}],"deletedEntries":[]}`.
7. Record the HTTP status code and response body from step 6.
8. `GET /api/v2/time/timesheets/<timesheetId>/entries` and confirm no entry was persisted for either of the rejected attempts (the timesheet's `data`/`sum` stay at whatever they were before steps 4–7 — empty/zero if no valid entry was ever saved in this test).

Expect: Both `PUT /api/v2/time/timesheets/<timesheetId>/entries` calls (negative duration `"-3:00"` and non-numeric duration `"abc"`) return HTTP `422 Unprocessable Content` — verified live — with body `{"error":{"status":"422","message":"Invalid Parameter","data":{"invalidParamKeys":["entries"]}}}`. Neither call persists an entry (confirmed live via the follow-up `GET .../entries`, whose `data` array/`sum` are unaffected by the two rejected attempts). For contrast, the same endpoint with a valid duration (e.g. `"03:00"`) was verified live to return `200`, confirming the payload shape itself is correct and the `422`s are specifically caused by the invalid duration values, not a malformed request.
