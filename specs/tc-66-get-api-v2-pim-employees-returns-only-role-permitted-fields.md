## Scenario: TC-66 — GET /api/v2/pim/employees returns only role-permitted fields and excludes sensitive fields for unauthorised roles

Starting state: no browser, no page, no storageState. Use the `request` fixture directly against the configured baseURL (http://localhost:8080/). No pre-existing auth — each identity is obtained on the request context's own cookie jar via the project's login helpers (`apiLoginAs`/`apiLogin` from `helpers/project-7/`, which perform the CSRF-scrape from GET /web/index.php/auth/login + form POST to /web/index.php/auth/validate).

Steps:
1. On a fresh `APIRequestContext`, authenticate as the seeded Supervisor/ESS-level login `baselinemanager` / `QaTool2026!Manager` via `apiLoginAs(request, 'baselinemanager', 'QaTool2026!Manager')`.
2. Send GET /web/index.php/api/v2/pim/employees?limit=5 using that session.
3. Inspect the response: verified live, this returns 200 with body `{"data": [], "meta": {"total": 0}, "rels": []}` — no employee records at all are visible to this account through this endpoint (not merely salary fields stripped from otherwise-present records).
4. On a second, independent `APIRequestContext`, authenticate as `qatooladmin` / `QaTool2026!Seed` via `apiLogin(request)` (env-default admin credentials).
5. Send the same GET /web/index.php/api/v2/pim/employees?limit=5 request using the admin session.
6. Inspect the response: verified live, this returns 200 with `data` containing both seeded employees, each shaped as `{"empNumber": <number>, "lastName": <string>, "firstName": <string>, "middleName": <string>, "employeeId": <string>, "terminationId": null}` — no `salary`, `compensation`, or any other field is present anywhere in this body, matching the Supervisor account's response shape (once records exist) field-for-field. Re-request with `&model=detailed` and confirm it adds only `jobTitle`, `subunit`, `empStatus`, `supervisors` — still no salary/compensation field.

Expect (as originally scoped — see BEHAVIOR MISMATCH note above for verified actual behavior): the unauthorised role receives a 200 response that does not contain salary, compensation, or other restricted fields; the authorised role receives those fields in the response. Actual verified behavior: both roles get 200; the Supervisor login gets `data: []` (no visible records) while the admin login gets the full employee list, but in NEITHER case does the response ever contain a salary/compensation field — this endpoint does not expose that data to any role, so the field-level assertion this test case describes cannot be demonstrated against it.
